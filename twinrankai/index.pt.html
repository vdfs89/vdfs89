TwinRank AI

Um recomendador neural two-tower para e-commerce, treinado com 2,2 milhões de interações reais e avaliado com uma pergunta que a maioria dos portfólios pula: quanto da taxa de acerto é só mostrar ao usuário o que ele já viu?

Feito para a Fase 2 da Pós-Tech em Machine Learning Engineering da FIAP. Uma torre de usuário e uma torre de item aprendem embeddings de 64 dimensões a partir de visualizações, carrinhos e compras; o FAISS recupera candidatos, o Redis faz cache e uma API FastAPI responde. O pipeline inteiro roda de novo a partir de um clone limpo com um comando.

Arquitetura

Um pipeline reproduzível
por trás de uma API rápida.

O DVC versiona os 942 MB de dados brutos e encadeia os quatro estágios; o MLflow registra cada execução e o model registry decide o que a API serve.

Os manifests Kubernetes (Redis, probes, requests de CPU e um autoscaler de 2 a 6 réplicas) foram aplicados e validados num cluster kind local, não num provedor de nuvem.

Decisões de engenharia

Quatro decisões que valem explicar
numa entrevista.

01 · Avaliação

Separar o recall em repetição e descoberta.

O Recall@10 geral fazia o modelo parecer 36× melhor que a popularidade. Ao decompor, 90,5% dos acertos eram itens que o usuário já tinha visto, o que é esperado num modelo de embeddings só de ID, mas muda como o resultado deve ser lido.

Por isso o README mostra os dois números lado a lado, mais um teto de memorização, e nunca o recall geral sozinho.

02 · População

Avaliar só usuários que o modelo pode conhecer.

57% dos visitantes tinham uma única interação de treino e dominavam a média, levando o recall a um nível sem sentido. A avaliação agora cobre os 2.920 visitantes com pelo menos cinco interações de treino.

O README avisa que a mudança torna os números antigos e novos incomparáveis, para que uma queda aparente do baseline não seja lida como regressão.

03 · Reprodutibilidade

Um comando a partir de um clone limpo.

Os dados brutos ficam no DVC, não no Git, e o MLflow usa por padrão um file store local, então o pipeline roda offline, sem servidor para subir. A execução completa foi validada em outra máquina.

Duas versões registradas do modelo, treinadas em momentos diferentes com o código refatorado, deram métricas idênticas. Essa coincidência é a evidência de que o treino é determinístico.

04 · Serviço

Fallback em vez de erro.

Cada resposta diz como foi produzida: two_tower, popularity_fallback para visitantes fora do índice, ou unavailable quando nenhum checkpoint está carregado. Uma queda do Redis só custa o cache.

O serviço de treino fica fora do docker compose up de propósito, porque sobrescreveria o checkpoint que a documentação referencia.

Limitações

O que este projeto
não é.

  • As torres de item e usuário usam só IDs, então o modelo não recomenda itens que nunca viu no treino e só generaliza por co-ocorrência.
  • A maior parte do recall medido vem de repetir itens do histórico do usuário; o recall de descoberta é 0,0117.
  • A API roda localmente em Docker e num cluster Kubernetes local; ainda não tem URL pública.
  • O POST /train roda em background tasks do FastAPI: sem retry, sem progresso e disputando CPU com o serving. Produção exigiria uma fila de jobs.
  • O remote do DVC é um diretório local, uma escolha de escopo explícita para o desafio; em produção seria um bucket.
