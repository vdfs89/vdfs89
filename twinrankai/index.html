TwinRank AI

A two-tower neural recommender for e-commerce, trained on 2.2 million real interactions and evaluated with a question most portfolios skip: how much of the hit rate is just showing people what they already saw?

Built for FIAP's Machine Learning Engineering program, Phase 2. A user tower and an item tower learn 64-dimension embeddings from views, add-to-carts and purchases; FAISS retrieves candidates, Redis caches them and a FastAPI service answers. The whole pipeline reruns from a clean clone with one command.

Live demo

Train it on your own catalog,
in the browser.

The Streamlit app trains a small two-tower model and a FAISS index on the fly from two CSV files, products and orders, and returns recommendations per user. Sample data is built in, so you can try it without uploading anything.

It also shows the metrics comparison and a 2D projection of the trained item embeddings.

Hosted on Streamlit Community Cloud: if the app is asleep, it takes about 30 seconds to wake up.

Architecture

A reproducible pipeline
behind a fast API.

DVC versions the 942 MB of raw data and chains the four stages; MLflow records every run and the model registry decides what the API serves.

Kubernetes manifests (Redis, probes, CPU requests and a 2–6 replica autoscaler) were applied and validated on a local kind cluster, not on a cloud provider.

Engineering decisions

Four calls worth explaining
in an interview.

01 · Evaluation

Splitting recall into repetition and discovery.

Overall Recall@10 made the model look 36× better than popularity. Breaking it down showed that 90.5% of the hits were items the user had already seen, which is expected for an ID-only embedding model but changes how the result should be read.

So the README reports both numbers side by side, plus a memorization ceiling, and never the overall recall alone.

02 · Population

Evaluating only users the model can know.

57% of visitors had a single training interaction and dominated the average, pushing recall to a meaningless level. Evaluation now covers the 2,920 visitors with at least five training interactions.

The README says the change makes old and new numbers incomparable, so an apparent baseline drop is not read as a regression.

03 · Reproducibility

One command from a clean clone.

Raw data lives in DVC, not Git, and MLflow defaults to a local file store, so the pipeline runs offline with no server to start. The full run was validated on a separate machine.

Two registered model versions, trained at different times on refactored code, produced identical metrics. That coincidence is the evidence that training is deterministic.

04 · Serving

Fallbacks instead of errors.

Every response says how it was produced: two_tower, popularity_fallback for visitors missing from the index, or unavailable when no checkpoint is loaded. A Redis outage only costs the cache.

The training service is kept out of docker compose up on purpose, because it would overwrite the checkpoint the documentation refers to.

Limitations

What this project
is not.

  • Item and user towers use IDs only, so the model cannot recommend items it never saw in training and generalizes only through co-occurrence.
  • Most of the measured recall comes from repeating items from the user's own history; discovery recall is 0.0117.
  • The API runs locally in Docker and on a local Kubernetes cluster; it has no public URL yet.
  • POST /train runs in FastAPI background tasks: no retries, no progress and it competes with serving for CPU. Production would need a job queue.
  • The DVC remote is a local directory, an explicit scope choice for the challenge; a bucket would replace it in production.
