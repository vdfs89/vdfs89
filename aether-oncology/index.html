Aether Oncology

A clinical decision-support platform for oral-cancer risk. Its most important result is negative: a reproducible benchmark showed the model could not beat a coin flip, because the dataset had no signal to learn.

Started as a FIAP Tech Challenge. When the numbers looked too good, I benchmarked the PyTorch model against trivial baselines with 5-fold cross-validation, found the null result, removed every inflated metric and fabricated claim from the project, and documented the finding. The engineering around the model is the real deliverable.

Architecture

Engineering that holds
even when the model does not.

Two surfaces share one backend: a risk classifier behind /predict, and an experimental clinical copilot that streams its reasoning over server-sent events.

The README labels every capability by maturity. The safety judge and the physician override workflow are experimental, and the clinical tools (biomarkers, therapy matching) still return hardcoded data.

Engineering decisions

Four calls worth explaining
in an interview.

01 · Integrity

Publishing the result that looks bad.

Earlier versions showed metrics near 1.0. They were only reachable by the degenerate rule "predict positive for everyone" on a 70% positive dataset.

I synced every number to the benchmark and removed fabricated claims from the landing page: certifications, hospital counts and invented scientific citations. The null result is now the headline.

02 · Method

Diagnose the data before retraining.

Before trying a bigger model, I tested each risk factor against the target. With 160,292 rows, any real relationship would show up, and none did: the target in this synthetic dataset was generated almost independently of the features.

Removing the leaking columns barely changed the metrics, which confirmed there was not even signal to inflate.

03 · Audit

No audit record, no answer.

Every prediction is written to an audit log encrypted with Fernet and chained by hash, so a tampered entry breaks the chain. If the audit write fails, the API returns an error instead of an unaudited answer.

Before describing it, I checked the hash chain in the code, so one unsupported claim was not swapped for another.

04 · Resilience

Provider failure is a normal case.

The copilot routes LLM calls to Groq behind a circuit breaker; after repeated failures it opens, falls back to Gemini, and probes for recovery later.

Patient identifiers in Brazilian formats are scrubbed from telemetry before it leaves the browser, and conversation data stored locally is encrypted.

Limitations

What this project
is not.

  • The classifier has no predictive value on this dataset. A migration to a 25-feature dataset is in progress and its benchmark is still pending.
  • All data is synthetic. Nothing on this page or in the platform supports a clinical claim.
  • The safety judge runs on the copilot chat, not on /predict, and the physician approval workflow is experimental.
  • Clinical tools and the frontend LLM provider default to mocks; genomics, tumor board and FHIR integration are planned, not built.
