VITORIUM

An end-to-end MLOps pipeline that sorts medical texts by urgency: retrained by Airflow, shipped by GitHub Actions, served with ONNX Runtime and watched by Prometheus and Grafana.

The model is deliberately simple (TF-IDF and logistic regression). What this project shows is the engineering around it: parity checks that block a bad export, latency measured end to end instead of in isolation, and alert rules that are unit-tested before they ever fire.

Not a clinical tool. The dataset (Medical Abstracts TC Corpus, 14,438 abstracts) has no urgency labels. The three tiers are a heuristic regrouping of its five condition categories, made for an MLOps exercise. They do not reflect real triage protocols such as Manchester or ESI.

Low confidence: the model found few words it knows. It falls back to “normal” on text it does not understand, which is the most dangerous error in triage and one reason this is not a clinical tool.

How it works: the same TF-IDF vocabulary, IDF weights and logistic-regression coefficients as models/model.joblib, re-implemented in about 80 lines of JavaScript. Checked against scikit-learn on all 2,888 test texts: 100% same label, max probability difference 9e-7 (from rounding the weights).

Architecture

A pipeline,
not an isolated endpoint.

Batch retraining and real-time serving run the same training code. Training is deterministic (seed 42): the Airflow run reproduced the versioned metrics exactly, and every push retrains, exports and tests the model before packing it into the image the API serves.

Engineering decisions

Four calls worth explaining
in an interview.

01 · Errata

The 7.70× speedup was wrong, so I took it down.

Up to v0.1.1 the README claimed a 7.70× ONNX speedup. Then a parity check showed that the stock skl2onnx export was not the same model: it dropped the stop words, and 35 of 2,888 labels (about 1.2%) disagreed. It also failed to load in the slim Docker image because it depended on a system locale.

I rewrote the exporter, made the export fail whenever parity breaks, re-measured everything and kept the errata in the README. A faster model that answers differently is not the same model.

02 · Latency

4× in isolation, 1.35× where users feel it.

Pure inference got 4.09× faster. Through the API, the median request improved 1.35×, because HTTP, FastAPI and Pydantic take most of the 2.5 ms. I measured with two identical uvicorn servers that differed only in the backend, over five interleaved rounds of 300 requests.

Publishing only the 4× would have been easy. The 1.35× is the number that tells you where the next optimization has to go.

03 · Observability

Alerts are code, so they get tests.

Four Prometheus rules cover the API being down, a 5xx rate above 5%, p95 latency above 50 ms and a shift of more than 15 points in the share of any predicted class over an hour. That last one is a drift proxy that needs no ground-truth labels in production.

Each rule has a unit test run by promtool, and each has a response in the monitoring playbook. The Grafana dashboard is provisioned as code and comes up with the stack.

04 · Cloud

Cloud Run over a cluster.

For one stateless, CPU-only API with a 1 MB model, the design picks Google Cloud Run: it runs the container as is, scales to zero when idle and avoids the networking and IAM work of a Kubernetes or ECS cluster.

The bridge is built: every push to main publishes the image to GHCR, ready for gcloud run deploy. The cloud deploy itself was an optional bonus and was not done; the graded stack runs locally with Docker Compose.

Limitations

What this project
is not.

  • Not clinically validated. The urgency tiers are a heuristic proxy, and the classifier must not be used for real triage.
  • Trained only on English abstracts. Portuguese reports, or any text unlike the corpus, fall outside its distribution, as the demo shows.
  • The “normal” class is weak (precision 0.49) and is also the fallback for unknown text, which is the worst failure mode in triage.
  • The API has no authentication, and there is no Alertmanager: alerts show up in Prometheus but notify no one.
  • The API does not log the submitted text, but real patient data would still need a LGPD review, access control and a retention policy.
