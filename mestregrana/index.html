MestreGrana

A financial education assistant that answers from the user's own numbers, by text or voice, and falls back across three LLM providers so one outage does not take the chat down.

Built in Streamlit around a dashboard, financial reports (income statement, cash flow, variance), a product simulator and an audit page. The chat injects the user's investor profile, goals and latest transactions into every prompt and tells the model to say when the data is not there.

Architecture

Built to keep
answering.

The app was refactored into core, services, repositories and components, so the Streamlit pages only render and the provider fallback lives in one module.

Engineering decisions

Four calls worth explaining
in an interview.

01 · Availability

Three providers, one function.

Free LLM tiers rate-limit and go down. The chat calls call_llm_with_fallback, which tries Llama 3.3 on Groq, then Gemini, then GPT-4o-mini, and returns the first answer. Each call has a timeout; the single-provider path retries with exponential backoff.

Putting that in one core module meant the text chat and the voice chat got the same resilience for free.

02 · Grounding

Answer from the user's numbers.

Instead of generic advice, each prompt carries the user's income, goals, emergency reserve and latest transactions, plus an instruction to say when information is missing rather than guess the balance.

Voice answers are capped at one to three sentences, because they are meant to be heard.

03 · Data

A demo that needs no credentials.

The profile, products and transactions the chat reads come from versioned sample files, loaded through cached functions with a short TTL. Postgres on Neon, with a connection pool and health checks, backs the audit and consent records; MongoDB Atlas is optional.

So the public demo and local development run without any database secret, and the status panel shows which services are configured.

04 · Structure

From one big script to layers.

The first version was a single Streamlit file. The v2 refactor split it into core (logging, cache, LLM clients), services (cached loaders), repositories (Postgres and Mongo) and components (charts, tables, voice).

Optional dependencies, such as audio, are imported lazily, so a missing package disables one feature instead of crashing the app.

Limitations

What this project
is not.

  • It is a single-model chat with provider fallback, not a multi-agent system: there is no agent orchestration and no model that audits another model's answer.
  • Grounding is prompt injection of the user's data, not retrieval over a knowledge base; answer quality has not been evaluated.
  • The public demo runs on sample data only; it is an education tool, not regulated financial advice.
  • Password hashing uses salted SHA-256; a production version should move to a slow hash such as bcrypt or Argon2.
